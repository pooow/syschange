## 1. Обязательный TDD-цикл

**Правило:** Любое изменение логики (новая фича, исправление бага, рефакторинг) **строго** следует циклу Red → Green → Commit. Ассистент **не имеет права** предлагать код реализации до кода тестов.

### Шаг 1: Тест (Red State)

1. **Анализ задачи:**
   - Ассистент предлагает новые или обновленные тесты (в папке `tests/`)
   - Предоставляет **понятное описание на русском:**
     - **Зачем:** Какую бизнес-задачу или поведение проверяем?
     - **Что проверяем:** Какие конкретные условия считаются успехом? (asserts)
     - **Как работает:** Механика теста (моки, фикстуры, реальные вызовы)

2. **Предоставление кода:**
   - Ассистент дает **полный код файла теста** (Full File Replacement)
   - Не куски, не diff — полный файл с `#!/usr/bin/env python3` или аналогом

3. **Подтверждение Red State:**
   - Ассистент или пользователь запускает тесты: `pytest -v` (все тесты, не только новые!)
   - Подтверждается падение тестов (Red State) или ошибки импорта
   - Ассистент видит вывод и анализирует причины падения

### Шаг 2: Код (Green State)

1. **Только после Red State:**
   - Только после подтверждения Red State ассистент предлагает реализацию

2. **Полный код файлов:**
   - Ассистент дает **полный код всех измененных файлов** (Full File Replacement)
   - Не куски, не diff
   - Если файл большой — может быть разбит на логические секции с комментариями

3. **Проверка всех тестов:**
   - Ассистент или пользователь запускает **все тесты:** `pytest -v`
   - Подтверждается прохождение (Green State)
   - Критично: Ассистент должен видеть **весь вывод**

4. **Итерационное улучшение:**
   - Если тесты не прошли:
     - Возврат к Шагу 2 (исправление кода)
     - Или Шагу 1 (уточнение тестов)
   - Повтор до 100% Green State

### Шаг 3: Коммит

1. **Только после Green State:**
   - Ассистент предлагает `git commit` **только** после подтверждения всех тестов

2. **Команда коммита:**
   - Полная команда: `git add ...` + `git commit -m "..."`
   - Сообщение: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`)

3. **Атомарность:**
   - Один логический шаг = один коммит
   - Легко откатываемый: `git revert <commit>`

## 2. Правила предоставления файлов

**Важно:** Формат предоставления файлов зависит от возможностей инструмента AI и типа файла.

### Режим работы с прямым доступом к файловой системе (рекомендуемый)

Если инструмент AI имеет прямой доступ к файловой системе проекта (возможность читать/записывать файлы напрямую):

- **Все файлы (код, конфиги, документация):** Редактируются напрямую через инструменты файловой системы
- **Преимущества:**
  - Мгновенное применение изменений
  - Отсутствие ошибок копирования
  - Сохранение форматирования и кодировки
  - Автоматическое отслеживание изменений в Git
- **Процесс:**
  1. AI редактирует файл напрямую
  2. AI или пользователь проверяет изменения через `git diff` или просмотр файла
  3. AI или пользователь запускает тесты для подтверждения Green State
  4. AI предлагает коммит после успешного прохождения тестов

### Режим работы без прямого доступа к файловой системе

Если инструмент AI не имеет прямого доступа к файлам (работа только через чат):

#### Markdown-файлы (`.md`)

- **Формат:** Вложение (attachment, сгенерированный файл)
- **Способ:** Использовать скрипт для создания файла
- **Причина:** Корректное отображение в интерфейсе чата, возможность скачивания без копирования
- **Примеры:** `README.md`, `WORKFLOW.md`, `ARCHITECTURE.md`, `EXAMPLES.md`

**Пример создания MD-файла:**
```python
# Создание Markdown-файла через скрипт
with open('README.md', 'w', encoding='utf-8') as f:
    f.write(readme_content)
print("✅ Файл README.md создан и готов к использованию!")
```

#### Код и конфигурация (`.py`, `.yaml`, `.txt`, `.sh`, и др.)

- **Формат:** Полный код файла в теле чата (Full File Replacement)
- **Стиль комментариев:** Подробные, понятные, на русском языке
- **Примеры:** `syschange.py`, `config.py`, `test_config.py`, `config.yaml`

**Пример предоставления Python-кода:**
```python
#!/usr/bin/env python3
"""
Модуль для работы с конфигурацией.
Загружает параметры из config.yaml и предоставляет к ним доступ.
"""

import yaml
from pathlib import Path

def load_config(config_path: str = "config.yaml") -> dict:
    """
    Загружает конфигурацию из YAML-файла.

    Args:
        config_path: Путь к файлу конфигурации

    Returns:
        dict: Словарь с параметрами конфигурации

    Raises:
        FileNotFoundError: Если файл конфигурации не найден
        yaml.YAMLError: Если файл содержит некорректный YAML
    """
    config_file = Path(config_path)

    if not config_file.exists():
        raise FileNotFoundError(f"Config file not found: {config_path}")

    with open(config_file, 'r', encoding='utf-8') as f:
        config = yaml.safe_load(f)

    return config
```

### Правило комментирования кода

**Обязательно комментировать:**
- **Зачем:** Объяснять бизнес-логику и назначение кода
- **Почему:** Причины принятых решений (не очевидные из кода)
- **Граничные случаи:** Edge cases и их обработка

**Примеры хороших и плохих комментариев:**
```python
# ✅ ХОРОШО: Объясняет причину
# Используем timeout=30, так как Proxmox API может долго отвечать
# при большой нагрузке на кластере
response = requests.get(url, timeout=30)

# ✅ ХОРОШО: Объясняет бизнес-логику
# Пропускаем скрытые файлы (начинающиеся с точки),
# так как они не должны отслеживаться в системном мониторинге
if filename.startswith('.'):
    continue

# ❌ ПЛОХО: Повторяет код
i = i + 1  # Увеличиваем i на 1
```

## 3. Архитектура Проекта

### Каноническая структура

```
project/
├── docs/
│   ├── WORKFLOW.md            # Этот файл (правила для AI)
│   └── ...
├── src/ (или infra/, lib/, etc)
│   ├── config.py               # Единый модуль конфигурации
│   ├── main.py                 # Основная логика
│   └── ...
├── tests/
│   ├── conftest.py             # Фикстуры pytest
│   ├── test_config.py          # Тесты конфигурации
│   ├── test_integration.py     # Интеграционные тесты
│   └── ...
├── config.yaml                 # Конфигурация приложения
├── pytest.ini                  # Конфигурация pytest
├── pyproject.toml              # Зависимости проекта
├── .gitignore                  # Git ignore
└── README.md                   # Документация проекта
```

### Принципы архитектуры

1. **Разделение ответственности:**
   - `src/config.py` — единая точка доступа к конфигурации
   - `src/main.py` или аналог — основная логика
   - `tests/` — все тесты проекта

2. **Модульность:**
   - Каждый модуль решает одну задачу
   - Минимальные зависимости между модулями

3. **Тестируемость:**
   - Конструкторы и функции принимают зависимости (dependency injection)
   - Избегать глобального состояния
   - Использовать моки (unittest.mock)

## 4. Управление Конфигурацией

### Приоритет настроек (Single Source of Truth)

**Порядок (от высшего к низшему):**

1. **CLI аргументы** — Высший приоритет
   ```bash
   python main.py --param value  # Переопределяет всё
   ```

2. **config.yaml** — Основной источник
   ```yaml
   section:
     param: value
   ```

3. **Хардкод в коде** — ❌ Запрещен!
   ```python
   # ❌ НЕПРАВИЛЬНО:
   max_retries = config.get("max_retries", 3)  # 3 — хардкод!

   # ✅ ПРАВИЛЬНО:
   max_retries = config.get("max_retries")  # None если не найден
   if max_retries is None:
       raise ValueError("max_retries not set in config.yaml")
   ```

### Правила конфигурации

1. **Все параметры в config.yaml:**
   - Не использовать env vars в обход config.yaml
   - Не хардкодить дефолты в коде

2. **Единый модуль конфигурации:**
   - `src/config.py` — точка входа для всех частей проекта
   - Функции: `load_config()`, `get_param(key)`, `validate_config()`

3. **Валидация:**
   - При загрузке конфига проверить обязательные параметры
   - Выбросить `ValueError` с понятным сообщением при ошибке

4. **Тесты конфигурации:**
   - `test_config_loads()` — конфиг загружается
   - `test_config_required_params()` — обязательные параметры присутствуют
   - `test_cli_overrides_config()` — CLI переопределяет конфиг

## 5. Качество Кода

### Комментарии и Документация

1. **Docstrings для публичных функций/классов:**
   ```python
   def deploy_vm(template_id: int, snap_name: str) -> dict:
       """
       Развертывает виртуальную машину на основе шаблона.

       Args:
           template_id: ID шаблона в Proxmox
           snap_name: Имя снапшота для клонирования

       Returns:
           dict: {"id": vm_id, "ip": ip_address}

       Raises:
           ValueError: Если конфигурация неполная
       """
   ```

2. **Комментарии на русском:**
   - Объясняй **почему**, а не только **что**
   - TODO-комментарии для незавершенного функционала
   - Не удалять существующие комментарии без причины

3. **Примеры плохих комментариев:**
   ```python
   # ❌ ПЛОХО: Повторяет код
   i = i + 1  # Увеличиваем i на 1

   # ✅ ХОРОШО: Объясняет цель
   i = i + 1  # Переходим к следующему элементу (пропуская deleted)
   ```

### Логирование

1. **Структурированное логирование:**
   ```python
   import logging
   logger = logging.getLogger("myapp")

   logger.info(f"🚀 Starting deployment: {vm_id}")
   logger.warning(f"⚠️  VM exists, destroying...")
   logger.error(f"❌ SSH connection failed: {error}")
   ```

2. **Уровни логирования:**
   - `DEBUG` — внутренние переменные, шаги алгоритма
   - `INFO` — ключевые события (старт, завершение)
   - `WARNING` — ненормальные, но не критичные ситуации
   - `ERROR` — ошибки, требующие вмешательства

3. **Избегать спама:**
   - Не логировать прогресс-бары или polling в INFO
   - Фильтровать мусорные логи из зависимостей

### Обработка ошибок

1. **Явные исключения:**
   ```python
   # ❌ ПЛОХО: Молча возвращаем None
   def get_value():
       return config.get("param")  # None если не найден

   # ✅ ХОРОШО: Явная ошибка
   def get_value():
       if "param" not in config:
           raise ValueError("Required parameter 'param' not found in config")
       return config["param"]
   ```

2. **Graceful shutdown на Ctrl+C:**
   ```python
   try:
       deploy_vm(...)
   except KeyboardInterrupt:
       logger.info("🛑 Operation aborted by user")
       sys.exit(0)  # Не traceback!
   ```

## 6. Git Workflow

### Маленькие шаги

1. **Один тест = один коммит (когда возможно):**
   - Прошла группа тестов → коммит
   - Понятная история изменений

2. **Atomic commits:**
   - Коммит должен быть полностью откатываемым
   - `git revert <commit>` не должен создавать проблемы

3. **Сообщения коммитов (Conventional Commits):**
   ```
   feat: добавлена поддержка нескольких узлов
   fix: исправлена утечка памяти в parser
   refactor: переименована функция для ясности
   test: добавлены тесты для edge cases
   docs: обновлена документация
   chore: обновлены зависимости
   ```

### История проекта

1. **AI Ассистент ориентируется на последний коммит:**
   - Всегда проверяет текущую ветку перед предложениями
   - Анализирует, какие файлы уже изменены

2. **Проверка статуса:**
   ```bash
   git log -1 --oneline          # Последний коммит
   git status                     # Текущие изменения
   git diff                       # Что именно изменилось
   ```

3. **Особенность при множественных remotes:**
   - Если есть несколько удаленных репозиториев (origin, pq и т.д.)
   - Ассистент помогает настроить правильный push
   - Рекомендует: `git remote set-url --add --push origin <url>`

## 7. Чек-лист перед коммитом

**Обязательно выполнить перед `git commit`:**

- [ ] **Все тесты проходят:** `pytest -v` (все, не только новые!)
- [ ] **Код соответствует стилю:** Нет очевидных нарушений PEP 8
- [ ] **Docstrings добавлены:** Для новых функций/классов
- [ ] **Комментарии на месте:** Объясняют "почему"
- [ ] **Конфигурация валидна:** Нет хардкода в коде
- [ ] **Обработка ошибок:** `try/except` где нужны, graceful shutdown
- [ ] **Сообщение коммита:** Conventional Commits формат
- [ ] **Git history чистая:** Логические, откатываемые коммиты
- [ ] **Нет leftovers:** Все незавершенные файлы закоммичены
- [ ] **Изменения проверены:** `git diff` показывает ожидаемые изменения

## 8. Примеры применения

### Пример 1: Добавление нового параметра конфигурации

**Red:** Тест проверяет, что параметр читается из config.yaml
```python
def test_config_has_max_retries():
    config = load_config()
    assert "max_retries" in config["app"]
    assert config["app"]["max_retries"] == 3
```

**Green:** Обновляем config.yaml и src/config.py
```yaml
app:
  max_retries: 3
```

**Commit:** `feat: добавлен параметр max_retries в конфигурацию`

### Пример 2: Исправление бага с неправильной обработкой ошибок

**Red:** Тест проверяет, что при отсутствии параметра выбросится ValueError
```python
def test_missing_param_raises_error():
    config_empty = {}
    with pytest.raises(ValueError, match="required"):
        get_required_param("missing_key", config_empty)
```

**Green:** Обновляем функцию
```python
def get_required_param(key, config):
    if key not in config:
        raise ValueError(f"Required parameter '{key}' not found")
    return config[key]
```

**Commit:** `fix: добавлена валидация обязательных параметров`

### Пример 3: Обновление документации

**Задача:** Добавить новый раздел в README.md

**Действие (прямой доступ к ФС):** AI редактирует файл напрямую через инструменты файловой системы

**Действие (без прямого доступа):** Ассистент создаёт файл через скрипт
```python
with open('README.md', 'w', encoding='utf-8') as f:
    f.write(new_readme_content)
print("✅ README.md обновлён и готов к использованию!")
```

**Commit:** `docs: добавлен раздел с примерами использования`

## 9. Часто задаваемые вопросы

### Q: Что делать, если тест слишком сложный?
**A:** Разбить на несколько простых тестов. Каждый тест проверяет один аспект.

### Q: Можно ли использовать реальные зависимости в тестах?
**A:** Да, но предпочитай моки (unittest.mock). Реальные зависимости используй только для интеграционных тестов.

### Q: Что если config.yaml уже содержит параметр?
**A:** Ассистент проверяет текущий config.yaml и работает с существующей структурой.

### Q: Нужно ли коммитить config.yaml?
**A:** Да, если это пример конфигурации. Секреты (пароли, ключи) хранить в .gitignore.

### Q: Можно ли пропустить какой-то шаг TDD?
**A:** Нет. TDD-цикл обязателен. Если нарушено — пользователь пишет "Стоп. Нарушение TDD".

### Q: Почему Markdown-файлы предоставляются как вложения?
**A:** В режиме без прямого доступа к ФС Markdown-файлы в теле чата могут отображаться некорректно при копировании. В режиме с прямым доступом AI редактирует файлы напрямую, что исключает проблемы с форматированием.

### Q: Как понять, работает ли AI с прямым доступом к файловой системе?
**A:** Если AI может редактировать файлы напрямую (через инструменты вроде `str_replace_editor`), он работает в режиме с прямым доступом. В этом случае изменения применяются мгновенно и не требуют ручного копирования кода.
